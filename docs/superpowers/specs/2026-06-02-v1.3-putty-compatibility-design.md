# v1.3 PuTTY Compatibility Design

## Goal

Implement an opt-in PuTTY compatibility launcher MVP for bastion workflows. When a bastion client invokes a PuTTY-compatible command, sush parses the SSH launch arguments, opens a direct one-shot SSH session, preserves `Ctrl-\` SFTP switching, and exits after the session ends.

## Scope

- Add a Settings view reachable from the main TUI.
- Persist only the launcher enabled state and shim metadata in sush config metadata.
- Support Windows shim installation/removal in a sush-managed directory.
- Show unsupported/manual guidance on macOS and Linux without installing a shim.
- Add a PuTTY-compatible CLI entry that supports `-ssh`, `-l`, `-P`, `-i`, `-pw`, and `[user@]host`.
- Reject unsupported PuTTY modes and unsupported options instead of treating them as hostnames.
- Use `-pw` only as an in-memory temporary credential for the current connection.

## Architecture

The feature has three isolated units.

1. `putty_args` parses PuTTY SSH arguments into a one-shot target. It contains no TUI or SSH side effects, which keeps edge cases testable.
2. `putty_shim` manages the Settings-side launcher state and Windows shim files. On Windows it writes a sush-managed `putty.exe` script launcher in `~/.config/sush/putty-compat/`; on non-Windows it reports unsupported status and performs no install action.
3. `App` gains `Settings` and `PuttyDirect` runtime state. Normal startup remains unchanged. PuTTY direct startup constructs a transient `Host`, injects the temporary password into authentication, skips host history/config persistence, and exits the process when SSH ends.

## Data Flow

Normal startup:

1. `main.rs` sees no PuTTY compatibility marker.
2. `App::new()` loads existing config and starts in `Main`.
3. Users press `,` from Main to open Settings.
4. Settings reads and writes `metadata.putty_compat`.

PuTTY direct startup:

1. Shim invokes `sush --putty-compatible ...`.
2. `main.rs` parses the following args with `putty_args`.
3. `App::new_putty_direct()` creates a transient host with alias `user@host`.
4. The existing async connection path connects and authenticates.
5. Temporary password auth is attempted before stored-password lookup and before prompting.
6. SSH exit clears connection state and sets `should_quit = true`.

## Security Boundaries

- The temporary password stays only in `App` memory.
- It is never written to `hosts.toml`, system keyring, history, status messages, or connection labels.
- If the temporary password fails, sush can prompt interactively, but successful prompted passwords for PuTTY direct sessions are not saved.
- Unsupported PuTTY options fail with a readable error.

## Testing

- Parser tests cover supported forms, precedence, defaults, and unsupported option rejection.
- Store/shim tests cover default-off metadata, enable/disable persistence, platform status, and shim command rendering.
- App unit tests cover Settings navigation, Settings toggle behavior, and PuTTY direct exit behavior.
- Full verification uses `cargo check`, `cargo clippy -- -D warnings`, `cargo fmt --check`, and `cargo test`.
